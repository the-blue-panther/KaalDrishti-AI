# Chart engine upgrades for historical astrology testing

## What changed

- `AstroEngine.generate_chart` accepts an optional timezone-aware `reference_time_utc`. Runtime calculation time is retained separately in metadata. Historical transits, KP ruling planets, dasha-sandhi status, predictive-tech year, and transit Navatara can now be replayed at the forecast's actual issue time.
- Navatara uses actual Swiss Ephemeris transit longitudes instead of assigning every planet the midpoint of its transit sign.
- Chart metadata records the effective ephemeris flags/source and a per-component quality profile. Current environment reports Moshier for ordinary planets and the Swiss analytical routine for the mean node; do not assume requesting `FLG_SWIEPH` means the Swiss planetary files were used.
- Invalid coordinates/non-finite Julian Days fail early. DST ambiguous/nonexistent local birth times are rejected rather than silently selecting an offset.
- Vimshottari calculations normalize timezone-aware datetimes to UTC, use exact half-open period boundaries, expose exact ends in current/horizon lookups, validate lords/durations, and keep the configured 365.2425-day year explicit.
- Expanded full Vimshottari tree checks across 9 MD, 81 AD, and 729 PD nodes, including parent tiling, all PD start-time lookups, weight-product durations, and half-open semantics. This exposed and fixed sub-second truncation of intermediate `*_exact` boundaries; exact timestamps now retain microseconds. ChartState schema is 1.4 to mark output changes. Added a pinned Jyotishyamitra 1.4.0 full-tree fixture: all 9/81/729 lord nodes match and normalized parent-relative boundaries agree within 1e-9. Absolute calendar timestamps differ by up to 144 minutes across the synthetic 120-year cycle because Jyotishyamitra uses a 120-calendar-year span while this engine uses 365.2425 days/year. A real Delhi chart additionally compares 1,586 shared MD/AD/PD edges within 90.22 minutes. This validates period-tree arithmetic under stated conventions, not astronomical inputs or dasha meanings.
- Exact nakshatra-boundary longitudes are stabilized against floating-point underflow; the 81-point boundary grid covers start, midpoint, and near-end samples for every nakshatra.
- Added a full natal cross-check fixture (D1 sidereal longitudes, Ascendant, D9 signs) against Jyotishyamitra 1.4.0 for Delhi, 1990-12-01 10:30 IST. Its published package notes Swiss Ephemeris/Lahiri, so it independently checks chart implementation but is not an independent ephemeris family.
- Expanded divisional-chart reference comparisons to Sydney (1992), Toronto (1988) and Nairobi (2001) local-time cases, checking D3, D9, D30 and D60 Ascendant/Sun/Moon/Rahu/Ketu assignments against Jyotishyamitra 1.4.0. These add historical IANA-zone, hemisphere and chart-coordinate coverage but retain Swiss Ephemeris-family overlap; D60 remains school-sensitive.
- Fixed D27 and D40 starting-sign rules and corrected D60 sign placement; the Delhi sample now matches Jyotishyamitra on all 14 supported vargas above. The D60 rule is convention-sensitive and should be recorded as the selected interpretation, not treated as universally uncontested.
- Added range validation for varga longitudes/zodiac order and ulp-aware half-open boundary indexing for equal-part vargas. A D11 test exposed real underflow at repeated 30/11-degree edges after longitude normalization; the shared index calculation now stabilizes those boundaries. The four vargas without reference-package vectors have parity/start/boundary tests, but those tests do not settle their school-specific rules.
- Fixed the sunrise lookup to use the installed PySwissEph `rise_trans(jd, body, rsmi, geopos, ...)` API. The old positional call raised a `TypeError`, which had silently made Vaar fall back to the ordinary JD weekday. Sunrise results now include `sunrise_jd_ut` and `sunrise_status`; the Delhi 1990-12-01 fixture checks published sunrise rounding and the before/after-sunrise Vaar transition.
- Added an independent historical Panchang fixture for New Delhi, 1990-12-01 10:30 IST, covering tithi/paksha, nakshatra, yoga, karana and weekday labels; the published boundary windows are also tested. Tithi/Karana and Yoga transition roots agree with a separate Swiss-based implementation to about a minute or better. Krittika-to-Rohini is ~03:43:37 IST in the independent Jyotishyamitra implementation and this engine, versus ~03:49 in the published daily table; retained a 10-minute acceptance window and documented the disagreement rather than claiming exact agreement. Sunrise convention/rounding is separately allowed a few minutes.
- Applied a shared floating-point-safe half-open partition helper to Tithi, Nakshatra/Pada, Yoga, and Karana, then added exact-edge and just-before-edge Panchang tests. These confirm implemented arithmetic boundaries, not astronomical event times or broader panchang convention agreement.
- Wired ecliptic latitudes into planetary-war winner selection; previously chart generation omitted the optional latitude map, so tied/default latitudes made the first-listed planet win. Added circular longitude, strict combustion threshold/retrograde, latitude-winner, and chart-wiring tests. Traditional combustion thresholds and severity penalties remain convention-dependent/heuristic.
- Audited Gochar: the prior `TransitEngine` produced only a timestamped snapshot, with no transit-event search. Added deterministic Lahiri sign-ingress search using single-body ephemeris samples plus bisection, direct/retrograde direction, whole-sign house mapping relative to natal Lagna, strict timezone-aware dates, and safe sampling/tolerance bounds. `ChartState` now retains transit longitude and current whole-sign natal-house maps in addition to sign labels. Tests cover replay determinism and Saturn ingress/retrograde-return dates in 2020-2023; one published Lahiri dataset rounds the 2020 Capricorn ingress to 2020-01-24 04:27 UTC, while some other public astrology sources publish materially different clock times, so this is a pinned reference, not a claim of cross-source consensus.
- Added longitude-speed zero-crossing stations and caller-configured exact ecliptic-longitude contacts. Tests pin Saturn's 2020 retrograde station to a published Lahiri event within 90 seconds and Jupiter/Saturn's 2020 longitude conjunction to IMCCE within 15 seconds. This conjunction is specifically ecliptic longitude, not right-ascension conjunction or minimum angular separation. Broad body/date and edge-case coverage remains open.
- Added a process-global Swiss Ephemeris sidereal-mode regression: every chart calculation explicitly resets Lahiri because other libraries can mutate that global setting.
- Added a direct astronomical reference check against the Swiss Ephemeris manual's JPL Horizons Mars apparent-position example (2016-10-25 TT). The installed PySwissEph falls back to Moshier; the test records this fact and checks the observed sub-arcsecond residual against the published Horizons target.

Reference materials: [Swiss Ephemeris 2.10 manual, Appendix C, Test 3](https://www.astro.com/swisseph-download/doc/swisseph.pdf) and [Open Vimshottari Dasha Conformance Set](https://chartingstars.com/vedic-chart#vimshottari-conformance-set). The public Dasha set is method-conformance material, not independent astronomy validation; its cycle-display policy differs from this engine as described below.
- Feature extraction compares the dasha timeline against the chart's replay timestamp in UTC. Historical natal-feature dataset builds explicitly replay at birth time rather than the machine's present time; manifests fingerprint all chart-engine, feature-extraction, and feature-manifest source files.
- Three Bhinnashtakavarga table transcription errors were corrected. The fixed per-planet checksums now sum to 337, covered by a regression test.
- Corrected Ashtakavarga indexing to zodiac signs (1=Aries..12=Pisces), not houses rotated from natal Lagna. Fixed Ekadhipatya lordship pairs require zodiac coordinates. ML schema 1.2.0 briefly named these `sarvashtakavarga_sign_*`; schema 1.3.0 removes all Ashtakavarga features until table/shodhana references pass. Earlier datasets/artifacts were left intact and must not be relabeled or mixed with newer schemas.
- Ashtakavarga audit against BPHS Ch. 66-68 confirmed that sign coordinates are required and that Trikona/Ekadhipatya shodhana depends on zero-bindus and sign occupancy. The current shodhana helper has no occupancy input and reduces same-lord pairs unconditionally; it is not a faithful implementation of all printed cases. The conflicting Jyotishyamitra total 334 versus the standard BPHS total 337 is therefore not resolved by simply choosing either program. Raw BAV cells and both shodhanas remain unvalidated and are explicitly removed from ML schema 1.3.0+ and excluded from reliability scoring. Earlier schemas/artifacts are preserved, not relabeled.
- The 337 checksum is not proof that all Bhinnashtakavarga cells or shodhana are correct. On the Delhi reference chart, Jyotishyamitra's BAV totals 334 and its cell distributions disagree with ours; it is not a gold fixture. BPHS Chapter 66 terminology and edition-specific transcription still need a full cell-by-cell audit before changing the tables. Until then Ashtakavarga reliability features stay gated and are absent from ML schema 1.3.0+.
- Feature and chart metadata label approximate systems so they are not mistaken for equally validated measurements.
- Optional Jaimini/Kalachakra/additional-dasha and dasha-sandhi failures are recorded in `metadata.component_status` with a `calculation_failed:<exception type>` value instead of silently looking like an empty/no-period result.

## Verification

Run from the project environment:

```powershell
venv\Scripts\python.exe -m unittest discover -s tests -v
venv\Scripts\python.exe -m compileall -q chart_engine feature_extraction ml tests
```

Coverage includes full-chart replay determinism, a cross-implementation natal fixture across 14 vargas, a published Horizons astronomical vector, varga boundary/range checks, Vimshottari boundary checks, Panchang checks, combustion/war wiring, Gochar replay/ingress/station/contact checks, UTC/JD round trips, DST rejection, and Ashtakavarga invariants. Use the test runner output for the current count.

## What “reliable” means at this stage

This makes the engine a reproducible research harness; it does not prove all astrological systems correct or that astrology predicts outcomes. For a valid historical test, save the full chart and dasha output with engine fingerprint, effective ephemeris source, birth provenance, convention profile, and an explicit forecast timestamp that precedes the observed event. Do not use the current lifetime-marriage/occupation experiments as astrology reliability tests: they have outcomes but no archived, pre-outcome astrology claims and event windows.

The engine's profile marks Ashtottari approximate, Shadbala and several predictive features heuristic, KP ayanamsa/cusps approximate, and several other dasha systems experimental. Those outputs remain available for ordinary exploratory chart display, but they must be excluded from a reliability score until each subsystem has independent reference vectors. This is still a first validation tranche, not completion of the full chart-engine reference audit: additional dates/locations and independent vectors are still needed for Ascendant/house edge cases, D5/D6/D8/D11 and D2 convention resolution, Panchang limbs beyond the sunrise/Vaar regression, Ashtakavarga table semantics and shodhana, broader Vimshottari Moon inputs, and all retained dasha systems. Absolute Vimshottari boundaries must not be presented as second-level verified across different year conventions. Public Vimshottari sets use a birth-relative 120-year display horizon; this engine preserves a theoretical cycle whose first exact boundary can predate birth, so normalize representations when comparing.
