# Dasha + Gochar engine implementation and validation plan

This plan is based on the current `chart_engine` implementation as of 2026-10-01. It treats ephemeris/time geometry as measurable calculations and astrological rules as explicitly configured traditions. Nothing here promises event outcomes.

## Default profile and support boundary

- Time: timezone-aware UTC instants at the public API; IANA birth timezone resolution; UT Julian Day for Swiss Ephemeris. Never infer a timezone for naive input.
- Zodiac: geocentric sidereal Lahiri/Chitrapaksha; mean lunar node with Ketu exactly opposite Rahu; retain the actual effective ephemeris flag/source in every result. Current environment reports Moshier for planets, so precision claims must reflect that.
- Natal-house Gochar: Whole Sign from the natal ascendant. Other house systems are unsupported for timing outputs until their cusp vectors and boundary policy have independent fixtures.
- Vimshottari: nine-lord 120-year sequence; current implementation's 365.2425-day year and half-open `[start, end)` period ownership are the named profile. MD, AD and PD retain their nesting and exact UTC boundaries. Alternative year conventions are separate profiles, not silently mixed.
- Transit event geometry: sidereal sign ingresses, longitude stations, and configurable exact angular contacts are geometry-only. Aspect sets/orbs and transit interpretation are caller-selected profiles; no single Vedic school is assumed universally authoritative.

## Phased work and acceptance gates

1. **Core replay and provenance (current; partly done).** Lock Lahiri inside astronomy calls; ensure all time-dependent layers use one aware reference instant; store schema/profile/ephemeris flags, timezone database, calculation precision, and source hashes. Gate: same inputs/reference produce byte-equivalent event timestamps within the declared tolerance; invalid/naive timestamps fail loudly.
2. **Transit snapshots and rashi/house ingress (partly implemented).** Snapshot exposes longitude, sign, speed, latitude, and natal Whole-Sign house. Ingress search reports direct/retrograde direction and UTC root estimate; detect re-entries. Gate: published Lahiri event dates plus independent ephemeris/JPL position vectors, retrograde round-trip tests, sign-boundary tests, and query-window edge tests.
3. **Stations and exact contacts (implemented; initial references only).** Direct/retrograde stations are found by bracketing longitude-speed zeroes; caller-configured ecliptic-longitude contacts use continuous angular residuals and root finding. Saturn's May 2020 retrograde station agrees with a published Lahiri table to within 90 seconds. Jupiter/Saturn's 2020 ecliptic-longitude conjunction agrees with IMCCE to within 15 seconds. These are definition-specific geometry checks, not universal event times or validated Vedic aspect rules. Remaining gate: wraparound, near-grazes, multiple roots, repeated retrograde passes, and body/date matrix.
4. **Vimshottari boundary completion (arithmetic cross-reference passed; broader convention gate partial).** Exhaustive tests check 9 MD, 81 AD, and 729 PD nodes for duration products, parent tiling, and replay lookup. A pinned Jyotishyamitra 1.4.0 fixture now covers all 9/81/729 nodes at a nakshatra boundary; lord identities and normalized parent-relative boundaries agree within 1e-9. A real Delhi chart compares 1,586 shared MD/AD/PD edges, with a maximum absolute delta of about 90.2 minutes. Absolute dates in the full cycle differ by up to 144 minutes because Jyotishyamitra uses a 120-calendar-year span while this engine uses 365.2425 days/year. Keep the convention explicit; do not claim second-level date parity. Broader Moon positions/nakshatras and year-profile fixtures remain open.
5. **Dasha × Gochar event query (not implemented).** Given a natal chart, UTC interval, selected planet/event profile, and dasha profile, return transit events annotated with active MD/AD/PD at the exact event time and optionally a caller-defined window around it. Preserve provenance and don't promote a coincidence to prediction. Gate: deterministic replay, correct period assignment exactly on boundaries, event windows crossing MD/AD/PD boundaries, no future/outcome leakage.
6. **Convention/profile API and gating (partly done).** Put choices in an explicit immutable profile, attach it to outputs, and gate unsupported house systems, ayanamsas, aspect sets, and dasha years. Gate: changing a profile changes the profile fingerprint; unsupported combinations fail or return unavailable, never silently approximate.
7. **Production release evidence (not ready).** Full suite, compile, independent fixtures per supported claim, edge/performance tests over bounded date ranges, versioned reference data with source/license/version/tolerances, and a published readiness table. Prediction reliability remains separately outcome-calibrated; calculation conformance alone is not evidence of astrological predictive validity.

## Priority order

1. Finish reference-backed transit geometry and expose reproducible event outputs.
2. Expand MD/AD/PD cross-engine evidence to more natal Moon positions, nakshatras, and year-profile conventions; the full-tree arithmetic fixture is now pinned.
3. Add station and exact-contact event detection with explicit caller profiles.
4. Add dasha-at-event overlay and event-window replay.
5. Expand alternative ayanamsa/house/dasha traditions only when each has references and tests; otherwise keep them gated.

## Current baseline and gaps

- `TransitEngine` now exposes replayable position snapshots, sign/Whole-Sign natal-house ingress, longitude-speed stations, and configurable exact ecliptic-longitude contacts. A Saturn ingress, retrograde re-entry sequence, Saturn station and Jupiter/Saturn conjunction have pinned reference checks. It still lacks dasha-overlay event query, broad body/date references, and a formal immutable transit profile object.
- Ashtakavarga inputs are now passed and reported in zodiac-sign coordinates (1=Aries..12=Pisces), because the Ekadhipatya lord pairs are zodiac-fixed; they must not be indexed by houses rotated from Lagna. The ML feature schema was bumped so old house-labelled vectors are not silently reused. The 337 total is still only an invariant; matrix-cell and shodhana reference validation remain open, so exclude Ashtakavarga from reliability scoring.
- Review of the BPHS chapter text confirms that Trikona Shodhana has zero-bindus/equal-value conditions and Ekadhipatya Shodhana depends on planet occupancy. Current helpers do not encode those inputs/conditions. The 334-vs-337 conflict is unresolved at cell level; Ashtakavarga is intentionally absent from feature schema 1.3.0+ and remains excluded from reliability scoring.
- `VimshottariDasha` has 27×3 longitude samples and exhaustive internal full-tree arithmetic/boundary checks. A diagnostic one-chart JSM 1.4.0 comparison covered 1,586 timestamp endpoints with a maximum ~90.2-minute difference over the full 120-year horizon; the reference uses 365.25 days/year, while this engine uses 365.2425. The pinned MD fixture remains limited to a 60-minute ceiling, and the broader diagnostic is not yet a repeatable regression fixture. The public conformance vectors share the same convention and are labeled method-conformance only; a pinned, convention-reconciled external AD/PD fixture remains required.
- Astronomy output is deterministic within the installed Swiss Ephemeris/Moshier setup but not yet a high-precision JPL-family build for every body/date; source flags must remain visible.
- Whole Sign is the only supported natal transit-house profile. Interpretive transit effects and ML reliability are out of scope of numerical event detection and remain gated absent separate validation.
